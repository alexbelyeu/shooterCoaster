# On-ride photo: the default marker is 85% of the run, not of the lap (#701)

The issue asked for a default `photo` marker at "the lap's 85%". Every lap but the gym's is longer than a run
(level 1's is 147 s against a 60 s run, `ridePhysics.test.ts` `LAPS`), so 85% of the lap never comes round. The default is
where the ride is 85% of the way through the run (`photoMarker.ts` `photoDistance`, from the same `rideProfile` the spawner
plans with): late, before the end, on every level.

The gym's marker is at the start of the slow heartline roll through the Tree's gap (~53.6 s, `buildGymTrack`): the rider
upright, the gap and the trunk straight ahead. Inside the gap the car is rolled over (upside down at 56.5 s), which on a
score card reads as a broken picture, not a thrill.

The capture never reads the live canvas back on the spot: `createImageBitmap(canvas)` there stalled the capture's frame
~926 ms on CI (#710's three rounds). In an R3F after-effect, once the composer has drawn the frame (the drawing buffer
still holds it; no `preserveDrawingBuffer`, which would cost every frame), `canvas/gpuSnapshot.ts` blits it down to the
photo's size on the GPU into its own renderbuffer (WebGL2 `blitFramebuffer`, flipped so rows come back top first) and
queues `readPixels` into a pixel-pack buffer behind a `fenceSync`. Later frames poll the fence and copy the pixels out only
once it has signalled; a Web Worker (`canvas/ridePhoto.worker.ts`, `OffscreenCanvas.convertToBlob`) encodes the JPEG.
Photo mode (#828) keeps its `toBlob` on the canvas: the run is paused there, so a stall costs nothing. The smoke gates the
capture's frame at 2x a frame without it (the frame before, or the run's average), not a fixed ms, which on a software
renderer would only measure the runner.
