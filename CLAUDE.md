# ShooterCoaster — instructions for Claude

ShooterCoaster is a WebGL on-rails arcade shooter: you ride a rollercoaster through
themed biomes and shoot enemies against a timer. Owner: Alex Belyeu.

**This repo is developed autonomously by scheduled Claude sessions with no human
code review.** Alex reads a weekly report, watches the live `studio-status` issue
(generated by `scripts/studio-status.cjs`; never edit it by hand) and steers through
`docs/agents/STEERING.md` and GitHub issues labelled `steering`. Everything an
agent needs to know lives in this repo — sessions have no memory of each other.

If you were started by a scheduled task, run `scripts/pause-check.sh` first: if it
prints PAUSED, stop and reply with that line. Then read `docs/agents/PROTOCOL.md`, your
runbook in `docs/agents/runbooks/` and your role definition in `.claude/agents/` before
doing anything else.

## Commands

```bash
npm ci                    # install
npm run dev               # dev server (vite)
npm test                  # vitest unit tests for pure modules (~1s; `npm run test:watch` to iterate)
npm run build             # typecheck (tsc -b) + production build -> dist/
npm run check:bundle      # bundle-size budget (budgets.json)
npm run smoke             # headless playtest: title + every level + phone touch run (needs a build)
npm run verify            # test + build + bundle budget + smoke — run before every PR
```

Unit tests live next to the code as `src/**/*.test.ts` and run in plain Node
(`vitest.config.ts`): no DOM, no WebGL. Test pure logic (track curves, terrain
noise, scoring/stars in `src/levels/scoring.ts`, store actions, level configs);
keep pure helpers free of React/three imports so they stay testable. Adding a
level? `src/levels/LevelRegistry.test.ts` checks its `maxScore`, star thresholds
and `nextLevel` chain, and the curve/terrain tests sample its track automatically.

Headless browser in Claude cloud sessions: the Playwright CDN is blocked, so run
`export SC_CHROME="$(scripts/ensure-browser.sh)"` once per session before `npm run smoke`.
The smoke test writes PNG screenshots + `results.json` (frames, draw calls,
triangles, avg frame ms, kills, score, combat stats, on-screen enemy counts/sizes, errors)
to `e2e-results/`: `title.png`, and per level `<id>.png` (after a 10 s ride),
`<id>-enemy.png` (4× close-up of the largest on-screen enemy, time frozen), `<id>-combat.png`
(after 4 s of autofire + `killNearest(5)`, with the weapon's muzzle flash + tracer and the
gold hitmarker held on the kill frame via `holdFeedback`) and `<id>-results.png`. A level fails if
it gets no kills, a real mouse click doesn't fire, autofire never fires at on-screen
enemies, the `killNearest` hits never produce an `enemy:killed` (skipped if the
wall-clock level timer already ran out), the camera translates off the track pose at all
(kill feedback is rotation-only trauma, ≤ 1°, back to 0), the first-person weapon is off
screen / covers the centre / overlaps the HUD / points > 25° off the shot's tracer (also
checked in mobile portrait + landscape),
the camera aspect doesn't match the canvas (±0.01), or the results screen never appears.
`npm run smoke` also passes `--mobile`:
an iPhone 13-like touch context (390x844) taps PLAY and a level, then in portrait and
again in 844x390 landscape taps the canvas 10x, each tap 15–30 px off an on-screen
enemy (game time frozen while tapping), and requires kills (touch aim assist); checks
camera aspect == canvas aspect in portrait, landscape and after rotating back, that the
HUD is inside the viewport with no overlap in both orientations, and taps Pause (`mobile-level-select.png`, `mobile-level1.png`,
`mobile-level1-landscape.png`; `--skip-desktop` runs only that). **Look at the screenshots** with the Read tool — that is how you
playtest visually. Waits are polled against the frame counter because software
rendering can run at ~1 fps; tune with `--seconds`, `--combat-seconds`,
`--min-frames`, `--levels level1,level3`, `--shot-timeout <ms>` (default 120 s).
`drawCalls`/`triangles` depend on where the camera happens to be (frustum culling,
spawned enemies) and vary run to run; for before/after comparisons use the
camera-independent `scene` totals the smoke also prints (`track objs/tris` = objects
named `track*`).

Test hook: load the game with `?e2e=1` and use `window.__SC_TEST__`
(`levels()`, `startLevel(id)`, `frames`, `drawCalls`, `triangles`, `avgFrameMs`,
`errors`, `phase()`, `enemies()` → on-screen enemies with projected px, `stats()` → score/kills/combo/timeRemaining/phase/liveEnemies/
onScreenEnemies/shotsFired, `autoFire(on)`, `killNearest(n)` (fires one real shot,
then resolves hits via `processHit`, the bullet pool's own path), `enemyScreenPoints(n)`,
`endLevel()`, `setTimeScale(s)`, `rideTo` (set a track fraction 0–1 to jump the coaster there), `sceneStats()`, `combat` fire/hit/kill event counters,
`cameraTranslation` {current, max} = translation off the track pose (must be 0), `cameraTrauma`
{current, max} in degrees, `weapon` → the gun's on-screen box, pivot, muzzle tip + last shot point, `holdFeedback`,
`view()` → camera vs canvas aspect + FOV). See `src/testing/e2eHook.tsx`. Extend it when you need new test
surfaces. Bullets travel per *second* with a swept hit test (`combat/projectiles/bulletMotion.ts`),
but enemies and the camera still move a lot during one ~1 fps headless frame, so
autofire only sometimes lands hits — `killNearest` is what guarantees kills.
The coaster camera sets its own aspect/FOV from the canvas size (`track/cameraFov.ts`:
portrait screens get a wider vertical FOV); touch shots get aim assist (`combat/aimAssist.ts`).

## Stack

React 19 + @react-three/fiber 9 + drei + @react-three/postprocessing, three 0.172,
@react-three/rapier (physics), Tone.js (procedural audio), zustand (state),
framer-motion (UI), Vite 6, TypeScript strict. Deployed on Vercel: every push to
`main` goes to production at **https://shooter-coaster.vercel.app** (https://scoaster.com becomes the home once the domain is attached in Vercel). Preview deployments
are disabled (`git.deploymentEnabled` in `vercel.json`) — verification happens in CI. Serverless stubs in `api/` (leaderboard, daily seed, ghost
replays — currently in-memory placeholders).

## Skills in this repo

`.claude/skills/` has project knowledge — use it:
- `shooter-coaster-level-design` — **read before touching levels, enemies, decorations, terrain or landmarks.** It encodes hard-won rules (track extent formula, enemy scaling, z-fighting, terrain-following).
- `threejs-*` — three.js reference for materials, shaders, lighting, postprocessing, etc.
- `workflow-orchestration` — plan → execute → verify discipline.
- `branch-review` — the architecture/convention rubric the `pr-consistency` reviewer applies.

Commands: `/deslop` (`.claude/commands/deslop.md`) cuts AI slop from the files a branch
touches; builders run it before shipping. `/wrap-pr` runs the two independent reviewers
on a PR; QA runs it on every sizeable PR.

## Hard rules (all agents, always)

1. `main` must always build, pass `npm run verify`, and be playable. Never merge red.
2. Never force-push, rewrite history, or push directly to `main`. All changes go through PRs. Agents never merge: approval is the `agent:qa-approved` label and GitHub auto-merges (see PROTOCOL.md).
3. Never delete or disable an existing level, mode or feature without a playable replacement in the same PR.
4. No new paid services, accounts, API keys or secrets. No secrets in code. No new third-party network calls at runtime without a DECISIONS.md entry.
5. Only add assets you created (procedural / code-generated) or that are explicitly CC0, and record source + licence in `docs/ASSETS.md`.
6. Budgets in `budgets.json` are enforced by CI. Only the Director may raise them, with a DECISIONS.md entry.
7. Large rewrites (engine, renderer, state, physics) land behind a feature flag or in parallel modules until they reach parity — never a big-bang swap.
8. Dispose three.js geometries/materials/textures and Tone.js nodes you create; no allocations in per-frame hot paths. See `docs/HEAP-BOTTLENECKS.md`.
9. Keep this file accurate. If you change commands, structure or rules, update CLAUDE.md in the same PR.

"A DECISIONS.md entry" means a **new file** in `docs/agents/decisions/inbox/` (format in its README). Never edit `docs/agents/DECISIONS.md` directly: the Maintainer folds the inbox into it nightly, which keeps parallel PRs from conflicting.
