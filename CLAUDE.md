# ShooterCoaster — instructions for Claude

ShooterCoaster is a WebGL on-rails arcade shooter: you ride a rollercoaster through
themed biomes and shoot enemies against a timer. Owner: Alex Belyeu.

**This repo is developed autonomously by scheduled Claude sessions with no human
code review.** Alex reads a weekly report, watches the live `studio-status` issue
(generated by `scripts/studio-status.cjs`; never edit it by hand) and steers through
`docs/agents/STEERING.md` and GitHub issues labelled `steering`. Everything an
agent needs to know lives in this repo — sessions have no memory of each other.

If you were started by a scheduled task, run `scripts/pause-check.sh` first: if it
prints PAUSED, stop and reply with that line. Then read your runbook in
`docs/agents/runbooks/` and what it lists (normally `docs/agents/PROTOCOL.md` and your role
definition in `.claude/agents/`; the Builders and QA dispatchers read less) before doing
anything else.

## Commands

```bash
npm ci                    # install
npm run dev               # dev server (vite)
npm test                  # vitest unit tests for pure modules (~1s; `npm run test:watch` to iterate)
npm run build             # typecheck (tsc -b) + production build -> dist/
npm run build:portal      # the web-portal build (itch.io / Newgrounds / CrazyGames): relative paths, no analytics or share card -> dist-portal/ + dist-portal.zip (checked by scripts/portal/rules.mjs; needs the zip CLI)
npm run check:bundle      # bundle-size budget (budgets.json); also prints the startup JS (what index.html loads)
npm run smoke             # headless playtest: title + every level + phone touch run (needs a build)
npm run smoke:portal      # smoke the portal build served under /nested/path/ (title + level1 checks; CI `portal` job; needs build:portal)
npm run lighthouse        # Lighthouse on dist/ (vite preview), mobile + desktop: fails below SEO 100, Accessibility / Best Practices 95; Performance printed only (needs a build + SC_CHROME; e2e-results/lighthouse.json; docs/marketing/SEO.md)
npm run verify            # test + build + bundle budget + lighthouse + smoke — run before every PR
bash scripts/quiet.sh <cmd>    # run any noisy command with its output in a log file: prints status (+ failures and tail on error)
npm run og                # re-render the share card public/social/og-1200x630.jpg (needs a build) + the icons from public/favicon.svg (favicon.ico, apple-touch-icon, manifest icons/; `-- --icons` for just those, no build)
npm run clip              # render the level-1 gameplay clip (MP4 + GIF + stills) to docs/marketing/media/ in virtual time (needs a build + ffmpeg, ~15 min)
npm run audio:render -- --music <title|level1..5> | --sfx-sheet [--level id] | --mix <level>   # offline render of the game's sound → docs/audio/renders/<name>.{mp3,json,png} (needs a build + ffmpeg, ~20 s); add --engine scrim for the score engine + arcade SFX (--music also takes results); a --mix also renders its music alone to measure each kill against
npm run audio:render -- --score <file.scrim|vendored:1..6> [--engine port|original]          # one score alone through the port or the original Scrimshaw page (parity renders); --chain game plays a score file through the game's music chain
npm run audio:check -- <file.wav|mp3> [--kind music|mix|sfx] [--seam s] [--music stem.wav] [--strict]  # loudness, true peak, clipping, bands, seams, gun tail, kill over music vs the sound bible's targets
```

Unit tests live next to the code as `src/**/*.test.ts` (and `scripts/**/*.test.ts` for agent tooling) and run in plain Node
(`vitest.config.ts`): no DOM, no WebGL. Test pure logic (track curves, terrain
noise, scoring/stars in `src/levels/scoring.ts`, store actions, level configs);
keep pure helpers free of React/three imports so they stay testable. Adding a
level? `src/levels/LevelRegistry.test.ts` checks its `maxScore`, star thresholds
and `nextLevel` chain, and the curve/terrain tests sample its track automatically;
the smoke fails it until it has a `scene` entry in `budgets.json` (perf gate below).

Headless browser in Claude cloud sessions: the Playwright CDN is blocked, so run
`export SC_CHROME="$(scripts/ensure-browser.sh)"` once per session before `npm run smoke`.
The smoke test writes PNG screenshots + `results.json` (frames, draw calls, triangles,
avg frame ms, kills, score, combat stats, on-screen enemies, errors) to `e2e-results/`:
`title.png`, then per level `<id>.png` (the ride), `<id>-enemy.png`, `<id>-combat.png`,
`<id>-shot.png`, `<id>-results.png`, plus step shots (`level1-boss.png`, `level2-wave.png`, …)
and `mobile-*.png` with `--mobile`. Each level prints one summary line; a level fails on
blank or stalled rendering, unreadable enemies, missing kills or effects, page errors, or
the **perf gate** (`budgets.json` `scene` ceilings; only the Director raises them).
`drawCalls`/`triangles` vary with the camera: compare levels with the `scene` totals the
smoke prints. **The full list of what each step checks, its flags and the test hook
(`?e2e=1` → `window.__SC_TEST__`, the API the smoke and `npm run clip` drive) is in
`e2e/README.md`**: read it before changing `e2e/`, `src/testing/e2eHook.tsx` or anything a
smoke step checks, or when a failure needs more than its summary line.

## Stack

React 19 + @react-three/fiber 9 + drei + @react-three/postprocessing, three 0.172,
Tone.js (procedural audio), zustand (state),
framer-motion (UI), Vite 6, TypeScript strict. Fonts (Lobster, Inter) are self-hosted from `public/fonts/` (OFL); the game makes no
third-party request at runtime. `vite build --mode portal` (`build:portal`) is the same game with `base: './'` for web portals. Deployed on Vercel: every push to
`main` goes to production at **https://scoaster.com** (www.scoaster.com redirects there; https://shooter-coaster.vercel.app also still serves it). Preview deployments
are disabled (`git.deploymentEnabled` in `vercel.json`) — verification happens in CI. `vercel.json` rewrites only
the `/go/<campaign>` landing paths to the game; any other unknown path gets `public/404.html` with a real 404,
and it sets the security headers and a year's `immutable` cache on Vite's hashed `/assets/*` (so nothing unhashed goes in
`public/assets/`); `scripts/site.test.ts` models the routing and checks headers, share card, manifest and icons. `index.html` carries
the SEO head (meta, share card, `site.webmanifest`, `["VideoGame", "WebApplication"]` JSON-LD; the checklist and its sources are `docs/marketing/SEO.md`) and a visually hidden `#about` section
(outside `#root`, so it survives React's mount) that crawlers and screen readers read (the portal build drops the share-card tags, the manifest and the JSON-LD, keeps `#about`);
`src/app/indexHtml.test.ts` checks the JSON-LD, the one `h1` and that it names every level. There is no backend: scores and the Daily Run are saved in the browser.
Vercel Web Analytics (`@vercel/analytics`: page views, plus the `level_start` /
`level_complete` / `level_quit` custom events mapped from game-store phase changes in
`src/app/analyticsEvents.ts`, plus `share` (with its `method`) from the results screen's Share button via the `results:shared` bus event, listed in `docs/marketing/README.md`) is mounted in `src/main.tsx`
only on Vercel builds (`__BUILT_ON_VERCEL__`, set in `vite.config.ts` from `VERCEL=1`)
and never with `?e2e=1` (`src/app/analyticsGate.ts`), so dev, `vite preview`, CI and the
smoke tests send nothing. `?internal=1` marks a browser internal (localStorage flag, stripped
from the URL; `?internal=0` clears it, any other value is ignored): it sends nothing either, via the same gate and a
`beforeSend` that drops every page view and event while the flag is set. `applyInternalParam` decides once per page
load and the title's "internal: not tracked" marker reads that decision (`isInternalThisLoad`), so it shows even when
storage can't be written. Campaign links use landing paths `/go/<campaign>` (the catch-all rewrite serves the game there;
never redirect them, the page view's path is the attribution).

## Skills in this repo

`.claude/skills/` has project knowledge — use it:
- `shooter-coaster-level-design` — **read before touching levels, enemies, decorations, terrain or landmarks.** It encodes hard-won rules (track extent formula, enemy scaling, z-fighting, terrain-following).
- `threejs-*` — three.js reference for materials, shaders, lighting, postprocessing, etc.
- `workflow-orchestration` — plan → execute → verify discipline.
- `branch-review` — the architecture/convention rubric the `pr-consistency` reviewer applies.

## Context budget (all agents)

Everything you read stays in your context and is paid for again on every later turn
(cache writes were half of all studio spend in late Oct 2026; the token ledger now logs
each run's peak context, compactions, cache misses and heaviest tool results).

- This file is already in your context: don't Read it again.
- Run noisy commands through `bash scripts/quiet.sh` (`npm ci`, `npm test`, `npm run build`,
  smoke, `verify`, lighthouse, `audio:render`): it keeps the full log on disk and prints a
  status line, plus the failures and tail when it fails. `grep -n` / `sed -n` the log for more.
- Don't `cat` large files, logs or `results.json`: `grep -n` first, then Read with
  offset/limit; `jq` only the fields you need from JSON.
- Look only at the screenshots that answer your question (usually one or two), not every PNG.
- Don't poll or `sleep` waiting for CI or merges unless your runbook says to: a gap of over
  ~5 minutes between turns expires the prompt cache, and the next turn pays for the whole
  context again.

## Hard rules (all agents, always)

1. `main` must always build, pass `npm run verify`, and be playable. Never merge red.
2. Never force-push, rewrite history, or push directly to `main`. All changes go through PRs. Agents never merge: approval is the `agent:qa-approved` label and GitHub auto-merges (see PROTOCOL.md).
3. Never delete or disable an existing level, mode or feature without a playable replacement in the same PR.
4. No new paid services, accounts, API keys or secrets. No secrets in code. No new third-party network calls at runtime without a DECISIONS.md entry.
5. Only add assets you created (procedural / code-generated) or that are explicitly CC0, and record source + licence in `docs/ASSETS.md`.
6. Budgets in `budgets.json` are enforced by CI. Only the Director may raise them, with a DECISIONS.md entry.
7. Large rewrites (engine, renderer, state, physics) land behind a feature flag or in parallel modules until they reach parity — never a big-bang swap.
8. Dispose three.js geometries/materials/textures and Tone.js nodes you create; no allocations in per-frame hot paths. See `docs/HEAP-BOTTLENECKS.md`.
9. Keep this file accurate. If you change commands, structure or rules, update CLAUDE.md in the same PR.
10. Never create, fire, update or delete scheduled tasks or reminders: no safety-net check-ins, no `send_later`, `create_trigger`, `fire_trigger`, `update_trigger` or `delete_trigger`, even if a default habit suggests re-checking a PR later. Follow-up on every PR is already automatic: QA (on label) reviews it, Fix (on label) fixes what QA sends back, and the Maintainer sweeps anything stuck each night. End your session when your runbook's work is done. Only Alex, or his own interactive Claude session, manages scheduled tasks.

"A DECISIONS.md entry" means a **new file** in `docs/agents/decisions/inbox/` (format in its README). Never edit `docs/agents/DECISIONS.md` directly: the Maintainer folds the inbox into it nightly, which keeps parallel PRs from conflicting.
